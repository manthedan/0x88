# ORT Web 1.27.0 → 1.30.0: as-is native-WebGPU A/B

Date: 2026-10-10. Branch: `perf/ort-130`. Base: `5761490`.

## Decision: do not upgrade

Keep `onnxruntime-web` / `onnxruntime-common` at **1.27.0**. Only this evidence document is committed; the temporary package/lock edits and diagnostic harness were removed from the tracked change.

The unchanged-model candidate fails the no-regression condition:

- Warm physical-evaluation medians increase **27.5% (LQO), 82.4% (Maia3), and 36.0% (Centipawn ORT)**. Their three-session ranges do not overlap baseline ranges.
- Fixed-32-visit search also regresses substantially in those lanes.
- Native GPU outputs are deterministic within each version but differ between versions. BT4 changes its top policy move on the promotion fixture; LQO's maximum WDL probability difference is **0.01513671875**.
- DQL fold diagnostics are unchanged. Built workers boot successfully, including the separate CPU-only pair. The result is not a built-worker startup failure or silent switch to the WASM EP.
- The two measured search fixtures retain best-move/PV agreement. That narrower success does not excuse the latency regressions or establish parity for the entire search corpus.

No tuning, model conversion, precision change, graph rewrite change, batch change, deploy, push, or merge was made. The runtime's existing DQL rewrite remained enabled and unchanged.

### Harness exclusions

Early exploratory harness runs were discarded, not mixed into the table. A long awaited browser `eval` hit the CLI's 30-second IPC limit. The harness also stalled when requesting another adapter via `collectOrtRuntimeDiagnostics({probeAdapter:true})` after its search. The retained timing RPC instead receives the completed second-search result and terminates the worker **before that optional probe**. Its numeric capture, warm evaluations and both searches are already complete. A separate built diagnostic harness omits that adapter probe and returns final GPU API counters normally. The adapter was inspected on the page independently.

The initial Maia3 adapter incorrectly passed `[Loss, Draw, Win]` directly as PUCT WDL. Those initial Maia timing/search rows are **excluded** from every performance table. The adapter was corrected, rebuilt for both versions, and the entire Maia lane was repeated A/B/B/A/A/B under benchlock. Corrected raw tensors exactly match the original numeric captures within each version, and the corrected searches still have matching PVs between versions.

The IPC/probe limitations above were observed with the baseline too, not evidence of a 1.30 engine boot regression. The optional post-session adapter-probe stall is not diagnosed or fixed here.

## Kernel-profiler claim: confirmed unavailable on this native EP

The claim is correct for the selected native builds, not merely inferred from zero callback events:

- Installed 1.27 and unpacked 1.30 `lib/wasm/wasm-core-impl.ts` split JSEP initialization from native initialization. The native WebGPU branch invokes `webgpuInit` and sets `env.webgpu.device`.
- `env.webgpu.profiling.ondata` is invoked by `lib/wasm/jsep/backend-webgpu.ts` when its timestamp results are processed; the native initialization branch does not wire this callback.
- The actual built 1.27 t1 worker emitted **0 events / 0 reported kernel ms** while recording 26 GPU submissions and 32 async compute-pipeline creations on its first evaluation.
- All six 1.30 instrumented native sessions similarly emit no callback events despite the real GPU activity shown above, with timestamp-query support present.

Therefore the current `src/nn/ortRuntime.ts` / `src/lc0/onnxEvaluator.ts` zero kernel totals mean **unavailable**, not “zero GPU cost.” WebGPU API counters are independently available; they are not kernel timestamp durations.

The requested separate diagnostic code fix is **not committed**, because the rejected-upgrade instruction explicitly restricts this branch to this evidence document. An independent follow-up should expose an availability/reason status and unavailable (e.g. null) kernel duration rather than zero, propagate that distinction through timing deltas/reporters, and test disabled/no-data/real-data cases. Do not make an empty callback proof of WASM fallback.
